# LumiFace 演示与身份库批量扩充

日期：2026-10-17。

按当前 40 人演示库逐步操作的精简稿见 [现场演示操作稿](demo-walkthrough.md)，包括 Windows 下载取图、必填提示与三个身份验证例子。

## 一、演示前准备

1. 在 WSL 中启动：

   ```bash
   cd /home/zns/3_LumiFace
   bash scripts/start.sh
   ```

   已启动时不必重复执行。网页入口 http://localhost:5173，接口文档 http://localhost:8000/docs。

2. 提前在系统概览点击“加载模型”，确认权重已就绪、模型已加载。首次加载可能慢于后续推理。
3. 使用自己或已同意演示的人员照片：准备 2–5 名已知人员，每人 2–3 张注册照片，另准备同人的查询照片；再准备一位不注册的人员用于未知拒识。每张注册照片必须只有一个清晰人脸，单张 JPG/PNG 不超过 12 MB。
4. 同一个人的多张注册照片放在同一组，人工核实身份。系统不会自动判断文件夹中的所有照片是否属于同一个人。
5. 注册照片、校准照片和测试查询使用不同采集会话，不能把注册原图重新上传的成功当作泛化性能。
6. 先完整走一遍演示，记录实际成功与失败。批量实验可提前运行完，现场展示真实完成的结果与 CSV，无需现场下载模型或跑完整公开数据。

### 临时没有照片时的功能演示

本机已有 `work/astronaut.png` 和 `work/hopper.png` 两张公开功能样例。可通过 Windows 资源管理器打开 `\\wsl.localhost\Ubuntu-20.04\home\zns\3_LumiFace\work` 选取。只注册 astronaut，用 hopper 演示未知人员；不要事先把“未知人员”也导入身份库。注册图再次作为查询，只能说明功能链路运行，不能说明独立采集确认率。来源和使用范围见 datasets-and-licenses.md。

## 二、建议现场演示，约 8 分钟

| 顺序 | 页面与操作 | 讲解重点 |
|---|---|---|
| 1，约 30 秒 | 系统概览：展示人数、任务记录、模型状态 | 系统由光照增强、人脸检测、身份管理及实验评估组成，数据保存在本机 |
| 2，约 90 秒 | 图像增强实验室：上传真实暗光或逆光照片，比较原图、自适应、Gamma/CLAHE，查看直方图与下载 | 图像增强如何改变亮度和细节；正常图自适应保留原图是设计行为，不是处理失败 |
| 3，约 60 秒 | 人脸检测：同一张图运行双路检测，展示框、关键点、对齐裁剪与耗时 | 比较检测结果；增强是否改善需依据当前实际输出，不能保证每张都提升 |
| 4，约 60 秒 | 身份库管理：查看已批量导入人员；现场再演示一人多图注册与详情 | 照片经检测、对齐后提取特征；参考样本与自动编号保存在本地 |
| 5，约 90 秒 | 身份确认：1:N 上传已知人员另一张照片；1:1 选择指定人员；再上传未注册人员 | 已知匹配、指定身份验证、未知拒识，以及相似度与阈值的关系；未知结果以实际输出为准 |
| 6，约 90 秒 | 实验评估：切换 CBSR / Yale B 公开研究报告，展示方法、分母、区间及 CSV | 流程功能与性能证据分别解释。公开 NIR 没有完整夜间证据，受控光照不等于独立实景强逆光；95%/90%/95% 现场目标尚不能认定达标 |

可选增加 1–2 分钟：导入已准备好的小规模标注 ZIP，运行五组方法，展示任务进度、算法对比、分场景统计、逐样本与 CSV。正式统计应先校准并冻结阈值，再使用独立测试集。

演示身份确认时的默认 0.45 是功能演示值，不代表经过本次图库校准的准确率保障。扩大图库后应重新校准并测试，不为现场过阈值而临时挑选阈值后宣称达标。

## 三、两个导入入口不能混用

- 身份库管理 → 注册新身份：**每次新增一个人，上传该人的 1–10 张参考照片**。
- 实验评估 → 导入 ZIP：导入有框、身份、场景及会话标注的校准/测试数据，**不会自动注册人员或扩充身份库**。
- 公开研究报告使用独立研究图库，其人员不会自动出现在当前业务身份库。
- 网页现已支持“身份库管理 → 批量导入身份”。选择每人一个子文件夹的根目录，预览后开始导入。完整网页说明与已准备的 AT&T 数据路径见 web-identity-import.md。下面的脚本仍可用于命令行注册。

## 四、按人员文件夹批量注册

脚本已放在项目 `scripts/batch_import_faces.py`，无需额外安装 Python 包。

准备目录，例如：

```text
/home/zns/face_library/
├── 001_张三/
│   ├── front.jpg
│   └── side.png
├── 002_李四/
│   ├── front.jpg
│   └── side.jpg
└── 003_王五/
    └── front.jpg
```

Windows 可在资源管理器打开 `\\wsl.localhost\Ubuntu-20.04\home\zns`，创建 face_library 并放入照片。文件夹名将完整作为显示姓名，例如“001_张三”；系统中的数字 person_id 仍由后端生成，不取文件夹编号。这样也能区分同名人员。

每人文件夹仅放同一人的参考照片，1–10 张，格式 JPG/JPEG/PNG，不能嵌套子目录。采集前缀应表示真实注册会话。脚本给每人追加文件夹名形成 capture_id；不同采集批次使用不同前缀，不将注册、校准和测试会话混用。

先离线预检：

```bash
cd /home/zns/3_LumiFace
.venv/bin/python scripts/batch_import_faces.py /home/zns/face_library \
  --capture-prefix enroll-20261017-s1
```

这一步仅检查目录、文件数、大小和名称，不连接服务、不写入身份库，也不证明照片一定可检出人脸。

保持前后端服务运行，再在**另一个 WSL 终端**实际导入：

```bash
cd /home/zns/3_LumiFace
.venv/bin/python scripts/batch_import_faces.py /home/zns/face_library \
  --capture-prefix enroll-20261017-s1 \
  --apply --report work/face-import-result.json
```

网页仍打开 5173；脚本默认调用后端 http://127.0.0.1:8000。如后端端口有调整，显式指定 `--api http://127.0.0.1:8002`。脚本仅接受本机 HTTP 地址。

导入结束后刷新“身份库管理”，即可搜索人员、查看参考样本和用于身份确认。报告含成功的 person_id、样本数、跳过项及失败原因，不含照片或特征向量。

## 五、导入行为与失败处理

- 每个人单独提交事务。某人的任意一张照片无人脸、多人脸、重复或无效，则该人的整组注册失败；前面其他人员已经成功的记录保留。不会悄悄丢掉失败照片后继续注册该人。
- 已有同名人员默认跳过，防止重跑生成重复身份；不会覆盖或给已有身份追加照片。当前脚本只新增身份，页面的“编辑”也只修改姓名和备注。
- 文件数量超过 10、文件过大或目录格式错误会在预检阶段停止，先改正后再运行。
- 人脸数等推理检查发生在实际导入阶段。查看报告中 failed 的原因，修正该人的照片后可重跑；已成功人员会被跳过。
- 网络超时或服务异常可能无法确认是否已提交，脚本标记 uncertain 并停止剩余导入，不自动重复请求。先在身份库核对该人员，再决定是否重跑。
- CPU 环境依次处理人员，实际耗时随照片数量和设备变化，不显示虚构进度或成功数。
- 扩充图库会改变后续识别与未知匹配的分布。正式实验在扩库后重新进行阈值校准；旧图库的校准记录不应直接复用。

## 六、脚本验证范围

使用临时数据库、真实 SCRFD/ArcFace 权重及本机已有的公开功能样例验证批量调用。验证内容包括同一人多参考注册、无人脸拒绝、其他人员独立成功，以及重复执行跳过同名人员。没有向正式业务身份库自动添加演示人员；此验证不构成准确率基准。
